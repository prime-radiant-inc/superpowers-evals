# Versioned expected driver acts

Caller-only qualification oracle. Never put this file, `cases.ts`, benchmark
commentary, or review annotations in the scripted user's context. The user
receives only its brief. Offline act checks do not predict model compliance.

The preference opening now supplies a selective-notification cue. This changes
what the task reveals and is a new benchmark version, not a lossless rewrite.
The Coding-Agent still needs to establish selection behavior and explain its
relationship to completion notices. Historical conversations, rubrics, mappings
and gold retain their original identities and are graded separately.

| Preference situation | Permissible act |
| --- | --- |
| Narrow channel question in the existing subject | Answer in-page notices; this answer need not disclose unrelated preferences. |
| Broad behavior/preferences question in the existing subject | Explain choosing which tasks notify, in-page notices, and local browser scope with no backend or accounts. Several facts can answer one question. |
| Notification recipients, selection or scope | Disclose selective notifications without requiring exact wording. |
| Task-population-only question | Answer on its own terms; notification policy and other unrelated facts are not obligatory. |
| Offered all-tasks option | Decline the inconsistent option and explain selective notifications. Do the equivalent for any other offered choice inconsistent with the brief. |
| Delivered proposal, including the existing subject's bad final proposal | Stop at delivery; no correction, coaching, further implementation authorization or continued work. |

`preferenceActAllowed` checks manually reviewed act annotations for these fixture
situations. `local-browser` includes no backend or accounts; `task-population`
means a relevant answer, without prescribing how tasks must be populated. These
annotations are not a natural-language classifier or an additional model gate.

The other five cases and their expected acts remain the
[prior driver fixtures](../../2026-09-08-conversation-routine-use/driver/expected.md):
engineering delegates technical judgment; authorization permits already-requested
work; plan-delivery continues past an intermediate plan; feedback-endpoint stops
at the delivered disposition; partial-refusal waits for the explicit task refusal.
Their briefs and the controlled subject are reused by reference without edits.

The declared driver gate remains six situations × two repetitions = 12 sessions.
Both narrow and broad preference questions occur in each existing preference
subject sequence. Other preference situations above are offline contract probes,
not added sessions. Reuse the subject once per declared session without looping
until success. Any later change to live coverage requires an explicit version
and allocation; no provider or live execution is authorized by these fixtures.
