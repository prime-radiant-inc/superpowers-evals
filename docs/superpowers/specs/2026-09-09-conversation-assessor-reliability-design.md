# Conversation assessor reliability

Date: 2026-09-09 Pacific; user scope narrowed 2026-09-10 UTC.
Status: ordinary lifecycle/capture/accounting and offline analysis are retained;
the bespoke diagnostic execution/preparation/authority design is retired.
Source integration is explicitly permitted before live qualification. The
candidate remains empirically unqualified. No deployment/provider authority
follows from source merge, and earlier stopped allocations remain closed.

## Current user-directed scope

Retain Quorum's role/completion/conversation/accounting integrations and the
existing Gauntlet assessment lifecycle, SDK boundary capture and physical-attempt
accounting. Retain semantic data, shared qualification mechanics and offline
reconstruction/native classification. The deferred-handler fixture cleanup removes
a demonstrated test hazard; historical timeout attribution remains unresolved.
The existing 15-second fixture bound and 200ms kill grace are unchanged.

Remove the dated parent/child launcher, execution/preparation/authority/relocation
modules and live SDK loop. Reconstruct only offline evidence and its review;
no new diagnostic allocation/proposal is emitted. Preserve every historical
source/data identity, receipt, manifest, package and negative result. There is no
replacement framework or operator command; retained qualification modules are
inactive as an operator workflow. The source worker stops at a successor commit;
the existing integration coordinator handles push/merge.

The operator route is the existing `evals-appliance campaign register|list|run|status|cancel|costs|report`
interface. Ordinary `quorum run` → `runScenario` → `runPreparedConversation` →
`invokeGauntletRole` → `gauntlet assess` worker execution runs beneath it. The
earlier dated `conversation-routine-use/run.ts` is an old campaign-helper wrapper,
not a second active runtime; `qualify.ts` is not another operator. The normal assessment
CLI currently starts fresh history and does not expose the supported internal
body-capture/physical-cap options. Exact frozen-prefix resume and that CLI
plumbing are documented gaps only. Scenario post checks precede assessment and
cannot inspect a later report. No live/deployment work is authorized here.

It is not a dispatch, launcher/provisioning recipe or prerequisite for the current

## Outcome

Conversation evals must produce a valid, evidence-grounded assessment within
their declared limits, or an explicit operational failure with retained evidence
and honest cost coverage. A maintainer must be able to distinguish a malformed
report, a wrong grade, an interrupted request and a failed Coding-Agent task.

This work addresses three connected defects: malformed report arguments,
unsupported grading inferences, and timeout finalization. It preserves the
ordinary Gauntlet/quorum workflow and the broader
[routine-use release requirements](2026-09-08-conversation-evals-routine-use-design.md).
A mechanical fix alone does not complete that release.

## Evidence and uncertainty

The [research follow-up](../../experiments/2026-09-09-conversation-assessment-repair/research.md)
records the independent committee's findings and authenticated private evidence.
The [failed repair result](../../experiments/2026-09-09-conversation-assessment-repair/results.md)
remains the execution record.

Verified observations:

- Malformed SDK-returned tool inputs contain grading rows inside the reasoning
  string and omit the native criteria array. Gauntlet correctly rejects them.
- The symptom predates the ten-row rubric and latest prompt changes. A longer
  ten-row response succeeded. Neither expansion nor a simple output-token
  cutoff explains the defect.
- One historical three-row assessment recovered after five rejected submissions.
  The observations do not isolate whether feedback, shortening, history or a
  fresh generation enabled recovery.
- The latest grader drafts credit a notification policy absent from the
  proposal. All decisive read payloads were delivered unchanged.
- The assessor and parent use overlapping 120-second allowances. A parent kill
  during a request can prevent normal child finalization.

Model generation versus provider parsing is unresolved. Public reports and
generic tool documentation support a possible representation failure, not a
confirmed Sonnet 5/Mantle defect. A local SDK fixture does not reproduce provider
generation or establish grading accuracy. Heterogeneous historical runs do not
establish error rates.

The repair may qualify an effective mitigation without access to provider
internals. It must accurately state what was reproduced, what improved and what
remains unexplained.

## Chosen approach and scope

Use staged diagnosis followed by one integrated, evidence-supported candidate.
Lifecycle work and benchmark clarification can proceed independently of the
format investigation after this design is approved.

| Approach | Trade-off | Decision |
| --- | --- | --- |
| Capture the failing boundary, isolate a change, repair lifecycle and grading separately | Adds a small diagnostic step; permits targeted changes with assessable evidence | Recommended |
| Add more instructions or time immediately | Easy to implement, but repeats unisolated treatments and confounds recovery with latency | Do not select without diagnostic evidence |
| Replace assessment with multiple judges, per-criterion calls or a new report pipeline | Changes cost, semantics and interfaces together | Outside this increment |

In scope: assessment request cancellation and finalization; opt-in diagnostic
capture; a bounded reproduction and reduction workflow; a justified assessment
treatment; independently specified grading examples; and a versioned clarification
of the design scenario.

Preserve native report validation, exact criterion count/order, prior-request
evidence exposure, derived overall status, ordinary persisted valid-result shape,
subject/grader separation and accounting of every attempt. Keep generic Gauntlet
QA behavior unchanged. Any shared client interface addition must be optional for
unrelated callers and tested at their existing boundaries.

Do not extract XML or JSON from reasoning and accept it as a report. Do not add
majority voting, hidden retries, automatic provider fallback, case-specific
answers in runtime prompts, a general replay service, another campaign controller,
or a framework migration. A format change, model/endpoint change or larger role
budget requires a separately reviewed candidate decision before integration.

## Ownership and flow

| Component | Responsibility |
| --- | --- |
| quorum role runner | Own role deadlines, cancellation, child termination, process records and operational outcome |
| Gauntlet assessment CLI/loop | Propagate cancellation, stop request admission, validate newly returned native reports and finalize once |
| Provider adapter | Honor the assessment request's cancellation/deadline; expose diagnostic capture when explicitly enabled |
| Diagnostic caller | Reconstruct a frozen context, bound physical HTTP attempts, preserve each observation and classify it |
| Scenario and scripted user | Define visible intent and deterministic disclosure obligations without coaching the Coding-Agent |
| Qualification/readout | Keep format, semantic and overall outcomes separate while retaining every attempt in accounting |

The production path remains: quorum launches assessment; Gauntlet reads scoped
evidence; the Gauntlet-Agent submits a native report; Gauntlet validates and
derives status; quorum combines it with deterministic checks and execution state.
The diagnostic path submits a reconstructed context through the pinned SDK and
adapter, captures boundaries, classifies the reply and stops. It does not drive
a Coding-Agent or execute returned tools.

## Diagnostic contract

### Offline reconstruction

Reconstruct the logical context immediately before the latest first malformed
report, including spilled read payloads, complete message ordering, tool IDs,
thinking blocks/signatures, tool definitions and cache annotations. Pin the
executed sources, dependency lock, model, endpoint, region, effort, thinking and
output cap. Historical HTTP bytes were not retained: name the result a
reconstruction and hash its actual newly serialized request.

Compare the reconstruction against retained logs and frozen source behavior.
Reuse the existing real-SDK fixture for local preservation and correction
delivery; add checks only for new reconstruction, capture or limit behavior.
Keep private evidence, expectations and credentials out of committed fixtures.
The grader receives its rubric and evidence, never gold, external adjudications
or judgments from other assessment runs. Its own within-session submissions and
typed errors remain in history unless a declared diagnostic explicitly changes
that history.

### Retired first provider screen (historical only)

The first proposed screen permits at most three logical continuations and three
physical HTTP attempts total, whichever limit is reached first. SDK retries
consume the same physical-attempt allowance. Keep the original model and route,
run serially, and use no application repair loop. A non-report response, API
error or timeout consumes its admitted attempt and is not silently replaced.

For each attempt retain:

- logical request and physical attempt IDs, source/configuration and input hashes;
- credential-free request body and complete response body when returned;
- allowlisted response metadata: request ID, returned model, stop reason and status;
- SDK-returned content, adapted arguments and validation outcome separately;
- admission/return/abort timestamps, usage coverage and known cost.

Raw bodies stay in private appliance-owned artifacts. Capture must never write
authorization headers, cookies, credential projections or arbitrary headers.
Record body-capture failure as a diagnostic failure. Partial or absent bodies
remain explicit; do not claim a complete response from a log prefix.

| Observation | Conclusion and action |
| --- | --- |
| Malformation already in HTTP body | Local decoding did not originate it; model versus internal parsing remains unresolved |
| Correct HTTP body differs from SDK or adapted content | Investigate the identified local transformation |
| No malformation in the small screen | Inconclusive; stop |
| Only API errors or incomplete responses | Reproduction unresolved; stop |

The three-attempt limit is reconnaissance, not a reliability claim. There is no
automatic expansion. Before execution, freeze the concrete caller, reconstruction,
attempt/time limits and a conservative cost estimate that includes cache misses,
SDK retries and unknown usage. Use existing appliance ownership and credential
projection. An observed cost threshold is not a guaranteed invoice cap.

### Retired reduction/candidate gate (historical only)

If reproduction succeeds, choose a separately bounded comparison that changes
one factor while retaining the failing control. A synthetic schema/verbosity
matrix is useful only after checking whether reduction preserves the symptom.
A disappearing failure does not identify which removed feature mattered.

Recovery-history experiments may remove failed report/rejection pairs from model
context only as an explicit diagnostic condition, preserving the full audit
history and valid protocol pairing. Check the exact model's thinking/signature
rules before modifying context or tools.

Strict tools, another endpoint, output length and field order remain hypotheses.
The current properties already place criteria before reasoning. HTTP acceptance
of a strict flag does not prove enforcement, and current Sonnet 5/Mantle support
documentation does not establish that capability. Endpoint comparisons change a
serving stack and cannot uniquely locate its parser.

Before selecting the production format treatment, record its exact source/config
delta, baseline and treatment outcomes, plausible mechanism, counterevidence,
cost/latency effect and compatibility. Then freeze the integrated candidate for
independent review and qualification. Another general reminder alone is not a
diagnostic result. If no treatment is supported, report the format repair as
unresolved; independent lifecycle improvements may still be reviewable.

## Deadline and terminal-state contract

Retain the current 120-second outer assessment allowance and existing bounded
process cleanup. Allocate the final five seconds of that allowance to cooperative
cancellation and finalization: the initial work deadline is 115 seconds from the
parent's role start. This reserve is for local shutdown, not additional model
work and not a claimed empirical optimum.

quorum is the deadline authority. It supplies the child a deadline that includes
startup time; the child must not start a fresh 120-second allowance. Standalone
assessment derives the same work/finalization split from its own requested
allowance. Reject an allowance too short to contain the reserve before any
provider request. The implementation plan must define the CLI/client interface
and timing representation without changing historical command interpretation
silently.

Every request and SDK retry must check remaining work time and share its abort
signal/deadline. No request may be admitted after cancellation or the work
deadline. A positive remaining budget permits a request only with its duration
bounded by that remaining budget; it does not promise enough time for a report.
At the work deadline, abort active work and begin finalization.

Assessment request metadata records physical attempt admission and settlement
even when raw-body capture is disabled. This makes SDK retries and unfinished
requests visible without retaining every production request body. Reuse existing
usage records; do not introduce a second pricing ledger.

Use one terminal transition so deadline, signal, response and writer completion
cannot finalize competing results. A valid report must finish validation and win
that transition before the work deadline to become an accepted assessment.
Returned usage is retained even when its response is too late to be accepted.
Do not append an invented verdict to an incomplete assessment.

| Situation | Required behavior |
| --- | --- |
| Valid native report before the work deadline | Persist the ordinary derived result and normal completion once |
| Malformed report while work time remains | Preserve input and typed error; any correction remains within the same deadline |
| Work deadline or explicit cancellation | Abort, admit no more work, retain known usage, finalize an operationally incomplete assessment |
| Parent must terminate an unresponsive child | Preserve the parent role/exit record and available evidence; no fabricated child report |
| Late reply or repeated shutdown signal | No second terminal result or promotion after stop |
| Finalization/write failure | Operational failure stays visible; partial output is not accepted |

For cooperative timeout, preserve Gauntlet's existing investigate-style timeout
artifact with no fabricated criterion grades, plus an explicit completion reason
in its event record. Cancellation must be distinguishable from timeout in the
retained events and quorum role state. It must not masquerade as a completed
uncertain assessment with valid criteria. Publish final files atomically.

The parent remains able to record a timeout/cancellation if the child cannot
write. No design can guarantee a child result after SIGKILL or storage failure.
quorum execution-error precedence remains authoritative even if a late or
partial result file exists. A stopped parent role cannot be promoted by a child
artifact. Known returned usage is counted once; unfinished requests retain
unknown coverage. Aborting locally does not prove provider-side billing stopped.

### Child completion record

New assessments emit a small versioned `assessment-completion.json` sidecar so
the parent does not infer timeout from prose or confuse it with a valid uncertain
grade. Version 1 contains `schema_version: 1`, the assessment `run_id`,
`status` (`completed`, `timed_out`, `cancelled`, or `errored`), a human-readable
`reason`, terminal timestamp and
`accepted_report_sha256` (a digest only for `completed`, otherwise null).
Here `completed` means a valid assessment, including a valid semantic fail or
unclear result; it does not mean the Coding-Agent passed.

Write the report and settled usage/events first, then publish this sidecar
atomically as the completion marker. It binds the exact accepted result bytes.
Publish at most one marker. A deadline or cancellation can stop model work while
finalization continues; it cannot turn a stopped operation back into completed.

The revised live quorum consumer requires a valid marker before accepting a
report from the revised assessment CLI. Missing markers, wrong run identity,
unsupported versions, digest mismatch and
contradictory completion/report data are operational errors. A cooperative
`timed_out` or `cancelled` marker supplies the corresponding parent stop cause
even when the child exits before the hard deadline. Existing parent cancellation
or timeout takes precedence over any child marker. If no marker can be written,
the parent preserves its existing role/exit record and reports incomplete
assessment; it does not manufacture a marker on the child's behalf.

The source pair must be deployed together for this live protocol. Historical
rendering and frozen result files retain their existing interpretation; no marker
is backfilled and no missing-marker fallback silently accepts a new live report.

## Grading and benchmark contract

A passing criterion needs evidence for the stated obligation. A plausible
alternative design does not supply an omitted fact. Complete evidence showing
an omission differs from unavailable evidence, and a rubric-permitted unresolved
choice need not fail.

Clarification and delivered proposal quality remain independent. For the watching
relationship, no particular field, UI control or terminology is required.
An explicit all-tasks policy can satisfy the relationship when the user/rubric
permits it; generic completion notices alone do not establish that agreement.
A policy must not be described as an acknowledged assumption unless the delivery
actually acknowledges it.

The proposed future design scenario includes a natural cue that the user only
cares about notifications for some tasks. The Coding-Agent still must establish
the selection behavior and explain the relationship. This is a new benchmark
version, not a lossless rewrite of the old opening request. Historical conversations,
rubrics, gold, mappings and outcomes keep their original bytes.

For that future version, the scripted user must disclose the selective-notification
preference when a question asks about notification recipients, selection, scope,
or broadly requests the remaining important preferences. A task-population-only
question is answered on its own terms. The user must not silently select an
offered all-tasks option inconsistent with the brief, invent implementation
details, coach after delivery or require exact question wording. A broad relevant
question can elicit several facts.

Retain separate judgments for adherence to the rubric and the scenario's validity
as a measure of requirements discovery. Do not rewrite historical expected grades
to fit a candidate response. An independently established historical gold defect
follows the original review/versioning procedure and cannot retroactively qualify
a candidate.

Freeze semantic controls before looking at candidate responses. Cover explicit
all-tasks agreement, unsupported inference, supplied requirements needing no
redundant question, independent clarification/proposal success in both directions,
permitted assumptions, unavailable evidence and chronology. Use the eight already
frozen repair controls where they cover these obligations; independently author
any missing counterexample before candidate evaluation. Do not embed these
examples or their expected answers in the runtime prompt.

## Verification and acceptance

Offline checks must establish behavior, not the presence of prompt strings:

| Area | Required evidence |
| --- | --- |
| Reconstruction/capture | Exact fixture bodies preserved at each boundary; credentials excluded; malformed input remains malformed |
| Attempt ceiling | SDK retry paths cannot exceed the physical-attempt cap; all started attempts remain recorded |
| Lifecycle | Controlled clocks and delayed/hanging transports cover startup delay, work expiry, cancellation, late return, repeated signal and writer failure |
| Process integration | The actual CLI and parent preserve an incomplete outcome when the child cooperates or must be killed |
| Report contract | Valid reports retain schema/status/exit behavior; unread references, wrong cardinality and embedded prose remain rejected |
| Scenario contract | Narrow and broad questions disclose the right facts; supplied requirements earn credit; no post-delivery coaching |
| Accounting | Every returned usage row appears exactly once; interrupted or unpriceable coverage never becomes zero |

Include a valid report whose terminal decision occurs just before 115 seconds
but whose atomic publication finishes during the reserve. It remains eligible
only if publication/marker validation completes before the parent's hard stop.
Exercise cancellation and writer failure at the same boundary; neither can
leave a partial result accepted or a stopped parent promoted.

Real-model evidence remains necessary for format reliability, grading and driver
behavior. Scripted responses and human review of control inputs do not qualify
the model.

The final candidate must pass the original 18-session retained assessment gate:
all 180 atomic judgments, original folds and decisive rationales must be sound.
Run the eight already frozen controls once each as a separate eight-session,
16-judgment check; every expected judgment and decisive rationale must be sound.
This proposes 26 assessment sessions before the driver gate, with the retained
and supplemental results reported separately. Both checks are binding parts of
assessor qualification: a miss in either prevents driver/campaign admission.
As in the original gate, a valid semantic miss fails the candidate but permits
the remaining declared assessment sessions for diagnosis; an operational,
required-evidence, settled-accounting or ownership failure stops further admission.
Any new counterexamples must be
listed and counted in the
execution proposal before admission; there is no implicit extra allocation.
A newly observed miss cannot be patched into the running candidate.

The driver must pass its full 12-session gate with explicit, versioned coverage
of broad/narrow preference disclosure and the revised scenario contract.
After both role gates pass, the unchanged 36-attempt campaign size and remaining
main/CI/canonical acceptance requirements still apply. Freeze the new scenario
version in the fresh cohort; do not combine it with old-version outcomes as one
treatment estimate.

Malformed attempts remain part of overall assessment reliability and cost.
Report first-submission format validity, eventual valid-report completion,
semantic agreement among accepted reports, overall successful sessions, retry
counts, latency and usage coverage separately. An eventual valid correction may
satisfy the original within-session contract; it does not erase failed submissions.
The qualification remains an observed fixed-set gate, not a statistical reliability
guarantee or a reason to silently remove failures.

## Superseded sequencing and release decision

1. Review and approve this design, including the proposed future scenario cue.
2. Write an implementation plan for offline reconstruction/capture, lifecycle
   repair, scenario/control preparation and their review.
3. Prepare the concrete bounded diagnostic execution proposal after offline
   validation. Earlier stopped identities do not supply new spending authority.
4. Use diagnostic evidence to select and review the format/semantic treatment;
   integrate with the independently verified lifecycle and scenario changes.
5. Freeze the candidate, all cases and the new full execution allocation before
   qualification. No source, gold or policy edits during a run.
6. Qualify, then follow the existing delivery requirements. If any gate fails or
   its allocation closes, preserve the failure and report exactly what remains.

This spec permits no automatic retry campaign, increased budget or repeated
candidate search. Ordinary implementation details within an approved plan do
not need individual approvals. A new provider boundary, larger role allowance,
materially different benchmark purpose or another candidate allocation is a
concrete scope decision.

The repair is complete only when the declared live checks establish usable format
and grading behavior, lifecycle failures are correctly represented, the reviewed
source pair passes required checks, and the preserved historical record remains
intact. The broader routine-use milestone additionally requires its ordinary
campaign, main/CI and canonical installation evidence.
